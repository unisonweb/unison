# Working on the JIT

How to build, run, test and look inside the JIT. The [design](design.md) says what it is and
[internals](internals.md) how each part works; this is the operational side. Numbers from
past runs are in [benchmarks/](benchmarks/).

## Building

- The JIT is always built in, and building needs no LLVM: nothing links against it, and
  `cbits/jit_llvm.c` carries its own copies of the few C API declarations it uses. LLVM is
  loaded with `dlopen` when the JIT is turned on (`--jit on`), at ucm's startup, and every
  function used is looked up with `dlsym`. Before the switch to loading at run time
  (2026-10-07) the JIT was behind a package flag and linked against one pinned LLVM.
- Any LLVM 20 or newer works (`brew install llvm`; 23.1.2 is what development uses). The
  shim looks in `UNISON_LLVM_LIB` (a path to the library) first, then on the dynamic
  loader's search path, then in Homebrew's `llvm` and `llvm@N` kegs, newest first, under
  `/opt/homebrew/opt` and `/usr/local/opt`, then MacPorts; on Linux in `/usr/lib/llvm-N`
  and the usual library directories. The oldest version accepted is 20 because
  `LLVMOrcCreateNewThreadSafeContextFromLLVMContext` appeared there; the IR generated uses
  nothing newer than opaque pointers (15) and `LLVMRunPasses` (17). Other versions than 23
  haven't been run yet: `UNISON_LLVM_LIB=/opt/homebrew/opt/llvm@20/lib/libLLVM.dylib` and
  the test transcript would be the check. When no usable LLVM is found ucm says so at
  startup, lists where it looked, and runs everything on the interpreter.
- Only macOS arm64 is built and tested so far. Nothing in the code generator is written
  per platform; what does vary is finding LLVM, reading the thread's C stack bounds for the
  stack guard, and whether LLVM guarantees tail calls on the target (it does on arm64 and
  x86-64).
- Iterate with `stack build --fast`. **Benchmark only on an
  optimized build, and keep it in its own work dir:** Stack does not rebuild when only the
  optimization level changes, so after a `--fast` build a plain `stack build` leaves the
  unoptimized binary in place. `.stack-work` is the fast tree and `.stack-work-opt` the
  optimized one:

  ```
  stack build --work-dir .stack-work-opt
  stack exec --work-dir .stack-work-opt unison -- ...
  ```

  Dependencies are shared between the trees, only local packages are built twice, and
  switching rebuilds nothing. On an optimized build "Count to 1 million" in `suite` takes
  about 40 ms; on a fast build about 3 s, which is the quickest way to tell them apart.
- A third tree holds the debug RTS for heap sanity checking, built once with
  `stack build --fast --ghc-options=-debug --work-dir .stack-work-debug`
  (`unison +RTS --info` then says `rts_thr_debug`). Run anything through it with
  `+RTS -DS -RTS` at the end of the command line: the RTS checks every heap object at every
  GC, which catches a bad info pointer, a wrong tag or a missed write barrier near its cause.
  About 10× slower. Some bugs only exist at `-O2` (GHC's optimized code trusts strict fields
  without checking tags), so there is also `.stack-work-optdebug`, the same over the
  optimized build.
- `Stack.hs`, `MCode.hs`, `Deque.Internal`, `Rope`, `Util.Text` and `Util.Bytes` carry
  `{-# OPTIONS_GHC -O2 -funbox-strict-fields #-}` in every build, because the closure
  layouts the generator and the C helpers rely on only exist in optimized code. Without it a fast build makes the layout probe turn the JIT off, which
  is correct, and the probe's log line says so.
- `cbits/jit_helpers.c` is also compiled to `cbits/jit_helpers.ll`, which is committed and
  embedded ("The IR helpers" in internals.md). After editing it or `cbits/jit_internal.h`, run
  `unison-runtime/cbits/gen-helpers.sh` (needs clang; the GHC headers come from `stack exec
  ghc`) and commit the `.ll` with the change; `gen-helpers.sh --check` says whether the two
  are in step. The build itself needs no clang: it only embeds the file.
- Stack ignores `lib/unison-util-rope/package.yaml` (the checked-in `.cabal` was generated
  by a newer hpack), so a new module, test or benchmark there goes into the `.cabal` file by
  hand. `unison-runtime.cabal` is regenerated by Stack's hpack and its version line changes;
  that is expected.
- Never run two Stack builds at once, and never leave a killed one behind: a build killed by
  a timeout leaves `Cabal-simple` and `ghc` processes holding the build lock, and later builds
  hang silently on it ("still blocking for directory lock"). Check with
  `pgrep -fl "stack build|Cabal-simple"`. A build can also hang at "Configuring
  unison-runtime" when macOS is waiting for the user to approve a binary that the configure
  step runs (`pkg-config` was the case); answer the prompt.
- Because every package depends on `unison-util-rope`, a change there rebuilds all the local
  packages in whichever tree is built next (about 5 minutes for `--fast`).

## Running

- `UNISON_JIT=on` compiles what gets hot on a background thread (the mode meant for use);
  `UNISON_JIT=eager` compiles every definition as it is loaded, synchronously, with no
  counters (for testing: deterministic, and it compiles code that never gets hot in a short
  run); `off` is the default. `unison --jit on|eager` is the same thing from the command
  line and overrides the variable. Either mode loads LLVM and runs the startup checks
  before anything else, and ucm prints one line saying the JIT is activated, or why not;
  `UNISON_JIT_LOG=1` adds the version and path loaded.
- Every other setting is an environment variable, parsed and documented in
  [Config.hs](Config.hs): the threshold and batch size, the copy and re-entry-batch limits,
  the exit and entry costs, `UNISON_JIT_DISABLE` (features turned off for bisecting a bug)
  and `UNISON_JIT_STRESS` (see Testing).
- The transcripts, all run from the repo root with
  `stack exec unison -- -C jit_codebase transcript.fork <file>`. `transcript.fork` runs on a
  throwaway copy of the codebase, so `jit_codebase` itself is never modified. Running one
  writes `<name>.output.md` next to it; for the idempotent one, copy the output over the
  `.md` when a change is intended, and don't commit stray `.output.md` files.

  | File | What it is | Codebase it needs |
  | --- | --- | --- |
  | `unison-src/transcripts/idempotent/jit-tests.md` | correctness tests with known answers, builtins only, prompt `scratch/main>`; the file contains its own expected output | any, including empty |
  | `unison-src/transcripts-manual/jit-benchmarks.md` | `jitSuite`, the benchmarks written for the JIT; prompt `jit-tests/main>`; timings print to the console, about a minute | `jit_codebase` |
  | `unison-src/transcripts-manual/jit-suite.md` | the older, broader `suite` (lists, maps, text, JSON, abilities), about 5.5 minutes per run; the test of whether the JIT is usable on library code | `jit_codebase` |

- `jit_codebase/` (repo root) has a project `jit-tests`, branch `main`, with the
  `@pchiusano/misc-benchmarks` suite (`suite`, `fibsuite`, `fib1`, `time`, `printTime`,
  `repeat`, ...) and the libraries `unison_base_7_19_2`, `unison_json_1_3_4`,
  `unison_cloud_20_15_1` and `mitchellwrosen_benchmark_2_0_0`. The test transcript runs in an
  empty codebase after `builtins.mergeio`, where the builtins keep their own names
  (`Nat.fromText`, not `Text.toNat`); `jit_codebase` has base, whose wrappers of the same
  names raise exceptions, so a stanza checked there alone can behave differently from the
  same stanza in the transcript.
- Unison gotchas met while writing the tests: with builtins only there is no `Nat.-`,
  `Nat.==` and so on, so the test transcript defines them in a prelude stanza followed by
  `update`; bare `==` and `<` resolve to the polymorphic `Universal` versions unless the file
  starts with `use Nat + - * / == < > <= >=`, and with `use Nat ==` in scope, `==` on anything
  but Nats won't resolve (write `Universal.==`); definitions in one `unison` stanza are not
  visible in the next unless a `ucm` stanza runs `update`; a `##`-qualified name at the end
  of a nested binding doesn't parse (base's `Raw` namespaces name the same builtins).

## Testing

The interpreter is the specification: every test runs the same program with and without the
JIT and the output must be identical. Most of the JIT's exit paths are rare in a normal run,
so the stress modes force them, and the failure mode of most bugs here is silent heap
corruption, so the debug RTS checks the heap.

- **The matrix**, on `jit-tests.md`, output identical each time:
  - `UNISON_JIT=off`, `eager`, `on`, and `on` with `UNISON_JIT_THRESHOLD=1` (every re-entry
    point is generated on first use, which tests the lazy path and is the most repeatable
    `on` configuration; what plain `on` compiles depends on the compile thread racing the
    program).
  - `eager` with `UNISON_JIT_STRESS=` each of `poll=3`, `ustack=4`, `cstack=2048`,
    `callee=3`, `alloc=64`, and all together with `pool=8`
    (`callee=2,cstack=4096,poll=5,ustack=4,alloc=64,pool=8`). `poll=N` fires the preemption
    poll every N entries; `ustack=N` starts the Unison stack tiny; `cstack=N` sets the C stack
    budget to N bytes; `callee=N` treats every N-th callee as not compiled; `alloc=N` makes
    the allocation budget N words; `pool=N` makes the constant pool's first array N entries
    so that it grows and functions check its size; `install=N` sleeps N ms before each
    function of a module is installed.
  - `on` with `THRESHOLD=1` and `install=5`, alone and together with the combination above.
  - `UNISON_JIT_DISABLE=worker` (the uniform form everywhere), and the stress runs with
    `UNISON_JIT_EXIT_COST=0 UNISON_JIT_ENTRY_COST=0`, so that the rules don't hide code from
    the tests; `UNISON_JIT_DISABLE=list,text,bytes,name` for the fallback paths of the C
    helpers; `UNISON_JIT_DISABLE=irhelpers` (generated code calls the C copies of the IR
    helpers) under the stress combination.
  - The helper self-tests: `eager` with `UNISON_JIT_STRESS=lists=20000,texts=20000,bytes=200000`,
    which run that many random operations through the C helpers at startup, each on the
    results of earlier ones, checking every result's structure and elements against Haskell.
    After touching either side of a helper, run a few hundred thousand steps (300,000 list
    steps take about 35 s on the optimized build), on the debug RTS too. In `on` mode these
    checks run on the compile thread and may not finish before a short transcript does; use
    `eager` for long ones.
  - On the debug RTS with `-DS`: the tests with `on` and `THRESHOLD=1`, with `eager`, with
    `on`, `THRESHOLD=2`, both costs 0 and `install=5,pool=8,alloc=64,poll=7`, and the
    benchmark transcript with `on` and `THRESHOLD=1`. Each takes 4 to 9 minutes.
- **Run the first few configurations on the optimized build too** before believing a
  benchmark. Some failures only exist at `-O2`, and the startup checks can fail closed there
  for reasons the fast build never shows (a sample list GHC floated to a top-level constant).
- **A transcript whose output matches says nothing about whether the JIT was on; the log
  does.** Run with `UNISON_JIT_LOG=1` and look for "the JIT is off" and for the compile
  lines. `UNISON_JIT_STATS=1` prints exit counts after every evaluation; the counts for
  "depth 1000000" are the quickest way to see whether frames are unwinding more than they
  should.
- The benchmark transcript is a test too, with the fast binary: base library code has
  shapes the builtins-only tests don't (a `Let` inside an inline binding was found by
  `printTime`, not by the tests).
- With the fast binary, `off` takes about 160 s and `on` or `eager` 10 to 25 s, because the
  tests are loops. A test run can go on a copy of the transcript in another directory, which
  lets several run at once; when several start at the same moment one can fail at once with
  an error about `unison.sqlite3-wal` or `credentials.json.lock` (the codebase copy racing
  another run's), so run that one again.
- The rope library has its own tests and benchmarks:
  `stack build --fast --test unison-util-rope` compares the Deque
  with `Data.Sequence` and the rope with a string model, checking the structures' invariants
  (`valid`) after every step (about a minute);
  `stack build --work-dir .stack-work-opt --bench unison-util-rope`
  runs the benchmarks (about 6 minutes; `--ba "--csv FILE"` for the numbers).
- Re-measure `off` whenever `enter`, `apply` or `yield` change: the interpreter's hot-count
  test is on the path of every call, and a version that compared with a configured threshold
  made the interpreter 5 to 20% slower with the JIT off.

## Looking inside

- `UNISON_JIT_LOG=1`: the compile log (per module: functions, compile time, IR size), why a
  combinator or part of one was left to the interpreter ("partly interpreted"), the startup
  checks and how long they took, the thread's C stack size, and "the JIT is off" with the
  reason when a check failed.
- `--jit-dump-ir DIR` (or `UNISON_JIT_DUMP_IR=DIR`) writes one `.ll` file per module into
  `DIR`, with the MCode of each function as a comment above its IR and a line for each
  combinator that wasn't compiled and why; `-` prints to stderr. Two versions of each module
  are written: `unison_<n>.ll` is the text handed to LLVM and `unison_<n>.opt.ll` the module
  after the optimization passes, which is what runs. For the arm64 assembly:
  `/opt/homebrew/opt/llvm/bin/llc -O2 unison_<n>.opt.ll -o out.s`. For example:
  `stack exec unison -- --jit eager --jit-dump-ir - -C jit_codebase transcript.fork t.md 2> t.ll`.
  Two dumps from different binaries differ in the info-pointer addresses baked into the IR;
  mask runs of ten or more digits before comparing them.
- `UNISON_JIT_DUMP_MCODE=1` dumps the MCode as it is loaded. To look at a site named in the
  statistics (`CIx ... <group> <n>`): run with `UNISON_JIT=off` and this, kill it once
  loading is done, and search the dump for `<group>:<n>:`.
- `UNISON_JIT_PASSES` is the LLVM pipeline a module is optimized with (the default is
  `defaultPasses` in `Config.hs`, the parts of `default<O2>` our code uses,
  [2026-10-09 pipeline](benchmarks/2026-10-09-pipeline.md); `default<O2>` for comparison;
  empty runs none) and `UNISON_JIT_CODEGEN_LEVEL` (0 to 3) the level of the JIT's target
  machine, for measuring what the optimizer and the backend cost and buy
  ([2026-10-09 O0](benchmarks/2026-10-09-o0.md)); full O0 with workers crashes, see there.
- `UNISON_JIT_EXITS=blocks` makes exits and unwinds write the frame back through generated
  blocks instead of the one call per site to `unison_jit_exit_frame` that is the default
  ([internals](internals.md#the-generator), "Write-back";
  [2026-10-09 exit call](benchmarks/2026-10-09-exit-call.md)). For comparison, and the
  fallback should the call form misbehave somewhere.
- `UNISON_JIT_INLINE_THRESHOLD=N` sets LLVM's inliner threshold (default 225), for
  measurement; `UNISON_JIT_SCHED=1` keeps LLVM's machine schedulers on (off by default,
  [2026-10-09 compile time](benchmarks/2026-10-09-compile-time.md)); `UNISON_JIT_LLVM_OPTS`
  is any further LLVM command line options, space separated. All go through
  `LLVMParseCommandLineOptions` at startup, in `jit_llvm.c`. To see where the backend's
  time goes, sample the harness: [2026-10-10 backend profile](benchmarks/2026-10-10-backend-profile.md).
- `UNISON_JIT_STATS=1` prints exit counts per site after each evaluation, with the compile
  totals first (modules, functions, auxiliary functions, re-entry functions generated on
  demand and never asked for, IR size, time, and the time split into generating the IR,
  LLVM's parse and optimization, and LLVM's code generation; the per-module log line under
  `UNISON_JIT_LOG` has the same split) and how often the trampoline entered each
  native function; `UNISON_JIT_STATS=each` prints the exits taken since the program last
  wrote output, after each write, which gives per-benchmark exits for a suite that prints a
  line per benchmark; `UNISON_JIT_STATS_EVERY=N` also prints every N exits, for evaluations
  that never finish. A run with statistics is at most 7% slower on the entries that exit
  most; quote timings from runs without them.
- `UNISON_JIT_TRACE=1` prints every native entry and exit, on both the C and Haskell sides.
  Unusable on programs that load base (it exhausts memory during the load); fine on the test
  transcript. `UNISON_JIT_TRACE_YIELD=1` prints each value native code yields, its pointer
  tag and closure type with its fields two levels down; cheap, and what found the
  untagged-pointer crash. `UNISON_JIT_TRACE_TEST=1` prints each startup self-test operation
  as it runs, for finding one that crashes.
- `UNISON_JIT_BUMP=0` makes every allocation call `allocate` instead of bumping inline, for
  comparison. `UNISON_JIT_DISABLE=...` turns features off one at a time; the list is in
  [Config.hs](Config.hs). Bisecting with it is how the exponential generator and the pool's
  lazy segment boxes were found.
- Profiling the trampoline: run the transcript in the background, `sample <pid> 5`, and
  resolve the addresses in the `unison` binary against `nm -n`. Haskell code shows up as
  offsets from the nearest exported symbol, which is coarse, but the C and runtime functions
  are named, and those were most of the waste when the round trip was cut in half.
- Per-thread state made before the settings are read is a trap: the self-tests once created
  the thread's JIT context before the stress settings were configured, and on that thread the
  stress poll fired on every entry forever. Under the stress modes the C entry now reports a
  function that leaves with the same exit a million times in a row without moving the stack.
- A crash in the GC is usually a bad object native code built or a pointer it stored
  untagged. The debug RTS over the optimized build puts the fault near its cause; macOS's
  crash reports (`~/Library/Logs/DiagnosticReports`) show which thread was where at exit
  time; `lldb` in batch mode needs `--source-on-crash` with the RTS's timer signals passed
  (`process handle SIGALRM SIGVTALRM SIGUSR2 -s false -n false -p true`), `PAGER=cat` and
  stdin closed, else it stalls on a prompt. A laziness leak on the compile thread shows in
  `+RTS -hT` as `:` cells.

## Benchmarking

- `suite` is the test of whether the JIT is usable on library code; `jitSuite` is the test of
  whether it is fast. Measure both.
- Optimized build only, from `.stack-work-opt`, on an idle machine, and never while another
  job is running. One run of `suite` is not evidence for a 20% change in a 20 ms benchmark;
  its run-to-run noise is about 5% both ways, and its `Remote.Ref` row is a single run of
  20 ms early in the suite that measures where a major GC lands, not the code. The first
  benchmark's label in the console output is overwritten by the transcript's progress line,
  so the first timing appears without a label.
- Record a run as a file in [benchmarks/](benchmarks/) named
  `<yyyy-mm-dd>-<what-it-measured>.md`: what the run was (build, mode, how many runs, which
  commit if it matters), the table, then what it showed. The
  [latest full run](benchmarks/2026-10-05-every-benchmark-end-of-m7.md) is what the next one
  gets compared against.
