# Working on the JIT

How to build, run, test and look inside the JIT. The [design](design.md) says what it is and how each part works, and [usage.md](usage.md) is the user's side (turning it on, installing LLVM, the settings); this is the developer's side. Numbers from past runs are in [benchmarks/](benchmarks/). [Part 1](#part-1-cheat-sheet) is the commands; [Part 2](#part-2-details) says why, and what goes wrong.

## Part 1: Cheat sheet

**Build.** Iterate with the fast tree; benchmark only with the optimized one, which lives in its own work dir so that switching never rebuilds:

```bash
stack build --fast                                  # iterate
stack build --work-dir .stack-work-opt              # benchmark
stack exec --work-dir .stack-work-opt unison -- ... # run the optimized binary
```

**Test**, from the repo root; the output must equal the file:

```bash
stack exec unison -- -C "$(scripts/testing-codebase.sh jit)" transcript.fork unison-src/transcripts/idempotent/jit-tests.md
```

Run it with `UNISON_JIT=off`, `on` and `eager` at least, and the [matrix](#the-test-matrix) before a commit that touches the generator or a helper:

```bash
scripts/jit-test-matrix.sh            # every row, fast build; --opt, --debug, --list, or row names
``` A matching output says nothing about whether the JIT was on: run with `UNISON_JIT_LOG=1` and look for the compile lines. Nor does it say that every module compiled: a module whose IR LLVM rejects is reported on stderr (`[jit] unison_<n>: JIT: adding a module: parse: ...`, with or without the log) and its functions stay interpreted, so after a change to the generated text, grep stderr for `[jit]` errors or dump the IR; `scripts/jit-test-matrix.sh` fails a row on one (found the hard way on 2026-10-31, when every module with a full-width worker was failing and the test transcript passed). A parse error is reported either way, but LLVM's *verifier* runs only under `UNISON_JIT_DEBUG` (`[jit] unison_<n>: JIT: adding a module: verify: ...`, and the module is refused); without the flag an IR that parses but is ill-formed is compiled and runs wrong, so after a change to the generated text run the transcript once with `UNISON_JIT_DEBUG=1 UNISON_JIT_LOG=1` and grep stderr for `verify:` (found the hard way on 2026-11-04: a helper whose entry block had become empty, so that the first arm, branched to, was taken as the entry; every module was refused under the flag and the transcript passed, and without it the same transcript failed with a value of the wrong shape). The transcripts proof (`scripts/proofs/transcripts.sh`, see the root [development.md](../../../../../development.md)) runs jit-tests.md with the JIT off like every transcript and then again under `UNISON_JIT=on` with `UNISON_JIT_THRESHOLD=5` in a fresh codebase, so a change that breaks native code fails the proof before full CI; it warns, rather than fails, when the log says the JIT didn't activate or compiled nothing (a machine without LLVM), and the CI `jit` job is the one that insists on native code, on every platform.

**Benchmark**, on the optimized build, on an idle machine, the two suites:

```bash
stack exec --work-dir .stack-work-opt unison -- -C "$(scripts/testing-codebase.sh jit)" transcript.fork unison-src/transcripts-manual/jit-benchmarks.md
stack exec --work-dir .stack-work-opt unison -- -C "$(scripts/testing-codebase.sh jit)" transcript.fork unison-src/transcripts-manual/jit-suite.md
```

Record a run as `benchmarks/<yyyy-mm-dd>-<what>.md`.

**Look inside.** `UNISON_JIT_LOG=1` (what compiled, what didn't and why), `UNISON_JIT_STATS=1` (exit counts per site), `--jit-dump-ir DIR` (the IR). The full list is in [Looking inside](#looking-inside).

**After editing `cbits/jit_helpers.c` or `cbits/jit_internal.h`:** run `unison-runtime/cbits/gen-helpers.sh` and commit the regenerated `.ll`; make some change to `jit_rt.c` too, or the C won't rebuild.

**Never run two Stack builds at once**, and check for a stuck one with `pgrep -fl "stack build|Cabal-simple"`.

**A build of one package can leave the executable stale.** After `stack build --fast unison-runtime` and `stack build --fast unison-cli`, a plain `stack build --fast` said nothing to build and `unison` was still the old binary (seen 2026-11-01: an error message added to `MCode.hs` was not in it, which `strings <binary> | grep` shows). Build the whole tree, or `stack build --fast --force-dirty unison-cli-main:exe:unison` to relink.

**How long things take** (Paul's machine; the fast tree unless said):

| What | Time |
| --- | --- |
| `stack build --fast` after a change in the runtime | 2 to 5 min |
| the same after a change in `unison-util-rope` (every package depends on it) | about 5 min |
| optimized build | about 5 min; debug RTS build about 8 min |
| `jit-tests.md`, JIT on | about 20 s |
| `jit-tests.md`, JIT eager | about 80 s on the fast build, 55 s optimized (every definition is compiled before it runs; 209 s optimized before 2026-11-06, when eager generated every `Let` body) |
| a stress row of the matrix | about 200 s |
| `jit-tests.md`, JIT off | about 160 s (the tests are loops) |
| `jit-benchmarks.md`, JIT on | about 5 minutes (each row runs for several seconds); with stdout redirected to a file nothing appears until the end, since it is block-buffered |
| the whole test matrix (`scripts/jit-test-matrix.sh`), fast build | about 20 min |
| `jit-benchmarks.md` (`jitSuite`), optimized | about 1 min |
| `jit-suite.md` (`suite`), optimized | 5.5 to 7 min per mode |
| `jit-replacements.md`, optimized | about 10 min per mode |
| 300,000 random list operations through the helpers (`lists=300000`), optimized | about 35 s |
| a test transcript on the debug RTS (`+RTS -DS`) | 4 to 9 min |

## Part 2: Details

### Building

- [The build trees](#the-build-trees): fast, optimized, and the two with the debug RTS.
- [The C side](#the-c-side): the embedded IR helpers, and why a header change alone doesn't rebuild.
- [Stack and Cabal gotchas](#stack-and-cabal-gotchas).

The JIT is always built in, and building needs no LLVM: nothing links against it, and [`jit_llvm.c`](../../../../cbits/jit_llvm.c) carries its own copies of the few C API declarations it uses. LLVM is loaded with `dlopen` when the JIT is turned on; where it is looked for and which versions are accepted is in [usage.md](usage.md#what-it-needs). macOS (arm64 and Intel), Linux (x86-64 and arm64) and Windows are built and tested, the Intel Mac, Linux x86-64 and Windows only in CI (`jit` job of test.yaml) and Linux arm64 also locally in an Ubuntu 24.04 container with gcc and Ubuntu's `llvm-20-dev`, where the whole matrix runs the same way; the test transcript truncates the transcendental functions to nine places because glibc's and macOS's libm differ in the last digit). Nothing in the code generator is written per platform; what does vary is finding LLVM, reading the thread's C stack bounds for the stack guard (`thread_stack_bounds` in `jit_rt.c`: macOS, glibc and Windows bodies), the symbols generated code resolves (none from the process: the runtime hands the JIT every helper's address, see [The IR helpers](design.md#the-ir-helpers)), and whether LLVM guarantees tail calls on the target (it does on arm64 and x86-64 except under the Win64 convention, where workers use a plain `tail call` and check the C stack at entry; `workerCC` in Codegen.hs). The C runtime compiles with any C compiler: the one routine that needs the `preserve_most` convention, the exit routine, is IR the JIT compiles at startup (2026-10-17).

#### The build trees

Stack does not rebuild when only the optimization level changes, so after a `--fast` build a plain `stack build` leaves the unoptimized binary in place. Each configuration therefore has its own work dir; dependencies are shared between them, only the local packages are built twice, and switching rebuilds nothing.

| Work dir | Build | Use |
| --- | --- | --- |
| `.stack-work` | `stack build --fast` | iterating; correctness tests |
| `.stack-work-opt` | `stack build --work-dir .stack-work-opt` | benchmarks, and the correctness tests before believing one |
| `.stack-work-debug` | `stack build --fast --ghc-options=-debug --work-dir .stack-work-debug` | the debug RTS: run with `+RTS -DS -RTS` at the end of the command line and it checks every heap object at every GC, which catches a bad info pointer, a wrong tag or a missed write barrier near its cause (about 10× slower; `unison +RTS --info` says `rts_thr_debug`) |
| `.stack-work-optdebug` | the same over the optimized build | bugs that only exist at `-O2`, where GHC's code trusts strict fields without checking tags |

The quickest way to tell a fast binary from an optimized one: "Count to 1 million" in `suite` takes about 40 ms optimized and about 3 s fast.

`Stack.hs`, `MCode.hs`, `Deque.Internal`, `Rope`, `Util.Text` and `Util.Bytes` carry `{-# OPTIONS_GHC -O2 -funbox-strict-fields #-}` in every build, because the closure layouts the generator and the C helpers rely on only exist in optimized code. Without it a fast build makes the layout probe turn the JIT off, which is correct, and the probe's log line says so.

#### The C side

[`cbits/jit_helpers.c`](../../../../cbits/jit_helpers.c) is also compiled to [`cbits/jit_helpers.ll`](../../../../cbits/jit_helpers.ll), and [`cbits/jit_exit.c`](../../../../cbits/jit_exit.c) (the exit routine, which is never compiled into the library) to `jit_exit.ll`; both `.ll` files are committed and embedded ([The IR helpers](design.md#the-ir-helpers), [Write-back](design.md#write-back)). After editing either `.c`, `cbits/jit_internal.h` or `cbits/jit_rt.h`, run [`unison-runtime/cbits/gen-helpers.sh`](../../../../cbits/gen-helpers.sh) (needs clang; the GHC headers come from `stack exec ghc`) and commit the `.ll` files with the change. Each `.ll`'s header names the SHA-256 of its sources (the `.c` and the headers it includes) and the clang that compiled them, so a diff shows whether a change to the C came with its regeneration; `gen-helpers.sh --check` compares that hash and, when the local clang is the one named, regenerates and diffs the IR, and says which of the two failed. With another clang it says so and the hash is the check: the text of the IR changes between clang versions (LLVM 19 began spelling constant field addresses as byte offsets, so Ubuntu 24.04's clang 18 differs from Apple clang 17 on every field access of the same code; the merge queue found this on 2026-10-25). The committed IR is what runs natively in every JIT'd process, so CI checks it on every PR (`ci.yaml`'s `verify-helper-ir`, the hash alone, which needs no toolchain) and in the merge queue (`test.yaml`'s build job runs `--check` on macOS and Linux; the regeneration happens on the runners whose clang matches, today the macOS ones). The build itself needs no clang: it only embeds the file. The C copy of the hash stays: the startup self-check runs it, and it is the fallback under `UNISON_JIT_DISABLE=irhelpers`.

The C runtime is one translation unit: `cbits/jit_rt.c` includes the `cbits/jit_builtins_*.c` files and the headers. A change to any of those alone doesn't recompile it: Cabal recompiles a C source only when it is newer than its object and knows nothing of its includes, and Stack runs Cabal only when a file it tracks changed. The included files are tracked (`extra-source-files` in package.yaml), so after editing one of them run `touch unison-runtime/cbits/jit_rt.c` before building; without the touch the stale object runs with the new Haskell, and a constant raised in a header and in Codegen.hs aborts at the old C bound.

#### Stack and Cabal gotchas

- Never run two Stack builds at once, and never leave a killed one behind: a build killed by a timeout leaves `Cabal-simple` and `ghc` processes holding the build lock, and later builds hang silently on it ("still blocking for directory lock"). Check with `pgrep -fl "stack build|Cabal-simple"`.
- A build can hang at "Configuring unison-runtime" when macOS is waiting for the user to approve a binary that the configure step runs (`pkg-config` was the case); answer the prompt.
- Stack ignores `lib/unison-util-rope/package.yaml` (the checked-in `.cabal` was generated by a newer hpack), so a new module, test or benchmark there goes into the `.cabal` file by hand. `unison-runtime.cabal` is regenerated by Stack's hpack and its version line changes; that is expected.
- Every package depends on `unison-util-rope`, so a change there rebuilds all the local packages in whichever tree is built next.

### Running

- [The transcripts](#the-transcripts): the four files and what each needs.
- [The codebase](#the-codebase): the `jit` testing codebase, where it comes from, and the differences between it and an empty one.

The modes (`--jit off|on|eager`), the settings and the replacements switch are described in [usage.md](usage.md#settings); every setting is an environment variable parsed in [`Config.hs`](Config.hs#:~:text=data%20Config). For tests, `eager` is deterministic and compiles code that never gets hot in a short run; `on` with `UNISON_JIT_THRESHOLD=1` is the most repeatable `on` configuration, since what plain `on` compiles depends on the compile thread racing the program.

#### The transcripts

All run from the repo root with `stack exec unison -- -C "$(scripts/testing-codebase.sh jit)" transcript.fork <file>` (the test transcript needs only builtins, so any up-to-date codebase does for it; without `-C` the home codebase is forked, which fails if that one is waiting to be migrated). `transcript.fork` runs on a throwaway copy of the codebase, so the downloaded one is never modified. Running one writes `<name>.output.md` next to it; for the idempotent one, copy the output over the `.md` when a change is intended, and don't commit stray `.output.md` files.

| File | What it is | Codebase it needs |
| --- | --- | --- |
| `unison-src/transcripts/idempotent/jit-tests.md` | correctness tests with known answers, builtins only, prompt `scratch/main>`; the file contains its own expected output | any, including empty |
| `unison-src/transcripts-manual/jit-benchmarks.md` | `jitSuite`, the benchmarks written for the JIT; prompt `jit-tests/main>`; timings print to the console | the `jit` testing codebase |
| `unison-src/transcripts-manual/jit-suite.md` | the older, broader `suite` (lists, maps, text, JSON, abilities); the test of whether the JIT is usable on library code | the `jit` testing codebase |
| `unison-src/transcripts-manual/jit-replacements.md` | `replacementSuite`, every replaced base operation at three sizes, meant to be run with `UNISON_JIT=off`, `UNISON_JIT=on UNISON_OPTIMIZATIONS=replacements` and `UNISON_JIT=on UNISON_OPTIMIZATIONS=-replacements` (the `time` helper runs each row for several seconds whatever its work) | the `jit` testing codebase |
| `unison-src/transcripts-manual/jit-continuations.md` | continuations captured inside the explosion's shapes, serialized under one optimization setting and resumed under another (design.md, "Continuations across processes"); run by `scripts/jit-continuation-matrix.sh`, every sender against every recipient, senders and recipients each in the interpreter and with the JIT on and eager, 24 runs, about three minutes on the fast build | the `jit` testing codebase |
| `unison-src/transcripts-manual/jit-nonmoving.md` | the non-moving collector's write barrier: two old arrays whose elements are swapped while a third keeps promoting fresh objects and garbage drives concurrent marks, with a checksum of both arrays at the end; prompt `jit-tests/main>`; run on the optimized build with `UNISON_JIT=eager` and `+RTS -xn -A4m -F1.1 -RTS` (about 20 s, must print 349997164999172), then again with `UNISON_JIT_DEBUG=1 UNISON_JIT_DISABLE=nmbarrier`, which must fail ("Testing" below) | the `jit` testing codebase |

**Loop state exploded** (design.md, "Loop state exploded"; `Unison.Runtime.MCode.Explode`) is on in every mode; `UNISON_OPTIMIZATIONS=-explode_args` switches it off (and `-explode_returns` the product-return worker below; every such switch is a name under that one variable, `Unison.Runtime.Optimizations`), for measuring it and for a process that has to resume continuations from one that ran without it. The test section "Loop state exploded" exercises the shapes; `UNISON_JIT_DUMP_MCODE=1` shows the k-th worker of a group as `<group>:<k*65536+32768>:<arity>` (98304, 163840, ...) and the calls to `#<hash>-98304`, and under a section's header the frames a continuation captured there is written out as, when they are not its own (`base <section>: [<frame>.<slot>, pack <tag> [...], ...]`, design.md "Continuations across processes"); a rewritten group's unoptimized copy is dumped under its own number, with no reference. The product-return worker (design.md, "Results exploded") is `<group>:32768:<arity>`, called as `#<hash>-32768` from a `Let` whose body takes the leaves; the test section "Results exploded" exercises its shapes, and under `UNISON_JIT_DUMP_IR` its LLVM worker returns that many pairs. `-known_constructor` switches off the two rewrites of design.md "Known constructors and case of case"; a join point is dumped as `<group>:<owner + k·2^48>:<arity>`, the k-th join point of the lambda at index `owner` (281474976710656 for the entry's first), and called as `#<hash>-<that number>` from the tails that build its constructor; the test section "Known constructors and case of case" exercises the shapes.

**The wide calling convention** (design.md, "The wide calling convention"; `Unison.Runtime.Wide`) is on exactly when the JIT is; `UNISON_OPTIMIZATIONS=wide` or `-wide` overrides that, so the interpreter can be run wide (`UNISON_JIT=off UNISON_OPTIMIZATIONS=wide`) and the JIT narrow (`UNISON_JIT=eager UNISON_OPTIMIZATIONS=-wide`). A compiled program's `.uc` carries the convention it was compiled under. The JIT compiles wide frames (workers return the result slots in registers, `padResults`). Native code must write every slot up to the frame depth before an exit can happen, the pad slots of a wide result included, because an exit writes the frame back from the allocas: an unwritten slot is a garbage pointer on the boxed stack and a GC crash that depends on when the collector runs. Run the test transcript and the serialization transcripts (`serial-test`, `random-deserial`) in both modes after a change to the emitter's frame layout or to `reflectValue0`/`reifyValue0`: the serialized continuation cases are byte-identical in both modes, and `serial-test-06` captures a continuation inside frames that hold call results, which are the wide variables.

The base library transcripts (`unison-src/transcripts-using-base/`) run through the transcript runner, `stack exec transcripts -- <prefix>`, which runs every transcript whose file name starts with the prefix with the `_base.md` prelude and checks its `.output.md`, under `UNISON_JIT=off`, `on` and `eager`. Exactly one prefix: given two arguments the runner silently runs every transcript of the repository instead (ten minutes), so `serial-test` and `random-deserial` are two runs; the ones that use `Map`, `Value` and hashing are `replacements`, `serial-test`, `all-base-hashes`, `hashing`, `codeops`, `binary-encoding`.

Callbacks from C (`FFI.newCallback`, trunk's unisonweb/unison#6306): `unison-src/transcripts-manual/dll-ffi-unix.md` runs a Unison function from a C callback inside a DLL call, re-entrantly too. Build its library as the CI `dll-ffi` job does (`clang -fPIC -c` then `clang -shared` on `dll-ffi/test.c` into `dll-ffi/libtest.so`, neither file is ignored, so delete them after) and run the transcript with `UNISON_JIT=eager`; the output must match the committed one. The callback's function is entered natively through the interpreter's `apply`, with no native frame below it since the `DLLCall` was a call-out (2026-10-22).

`run.compiled`: `unison-src/tests/jit-compiled.md` compiles a program (`jit-compiled.uc`, written to the current directory) whose loop matches on a type of its own; run the file with `unison run.compiled jit-compiled.uc` under `UNISON_JIT=eager UNISON_JIT_LOG=1` and expect the compile lines and `666668416667500000`. The CI `jit` job does this on every platform. The `.uc` format carries the data types' constructor arities since 2026-10-18 and a file is tied to the exact ucm version anyway, so compile and run with the same binary.

A test run can go on a copy of the transcript in another directory, which lets several run at once; when several start at the same moment one can fail at once with an error about `unison.sqlite3-wal` or `credentials.json.lock` (the codebase copy racing another run's), so run that one again.

#### The codebase

The `jit` testing codebase is a release of [unisonweb/testing-codebases](https://github.com/unisonweb/testing-codebases) (`jit-2026-10-19`, 17 MB gzipped). [`scripts/testing-codebase.sh jit`](../../../../../scripts/testing-codebase.sh) prints its directory, under `$TMPDIR/unison-testing-codebases/<sha256 of the archive>`, downloading and unpacking it only when that directory does not exist yet; `TESTING_CODEBASES_DIR` moves the cache. To publish a new version, pack `.unison/v2/unison.sqlite3` as a `.tar.gz`, make a release in that repository with it as the asset, and put the release name and the archive's SHA-256 in the script. It has a project `jit-tests`, branch `main`, with the `@pchiusano/misc-benchmarks` suite (`suite`, `fibsuite`, `fib1`, `time`, `printTime`, `repeat`, ...) and the libraries `unison_base_7_19_2`, `unison_json_1_3_4`, `unison_cloud_20_15_1` and `mitchellwrosen_benchmark_2_0_0`. It is on codebase schema 27; a codebase that needs migrating is migrated by opening it interactively (`UNISON_MIGRATION=auto` skips the prompt), not by `transcript.fork`.

The test transcript runs in an empty codebase after `builtins.mergeio`, where the builtins keep their own names (`Nat.fromText`, not `Text.toNat`); the testing codebase has base, whose wrappers of the same names raise exceptions, so a stanza checked there alone can behave differently from the same stanza in the transcript. Unison gotchas met while writing the tests: with builtins only there is no `Nat.-`, `Nat.==` and so on, so the test transcript defines them in a prelude stanza followed by `update`; bare `==` and `<` resolve to the polymorphic `Universal` versions unless the file starts with `use Nat + - * / == < > <= >=`, and with `use Nat ==` in scope, `==` on anything but Nats won't resolve (write `Universal.==`); definitions in one `unison` stanza are not visible in the next unless a `ucm` stanza runs `update`; a `##`-qualified name at the end of a nested binding doesn't parse (base's `Raw` namespaces name the same builtins).

### Testing

- [The test matrix](#the-test-matrix): the configurations a change to the generator or a helper should pass.
- [What else counts as a test](#what-else-counts-as-a-test).
- [Pitfalls](#pitfalls): the ways a passing test has lied before.

The interpreter is the specification: every test runs the same program with and without the JIT and the output must be identical. Most of the JIT's exit paths are rare in a normal run, so the stress modes force them, and the failure mode of most bugs here is silent heap corruption, so the debug RTS checks the heap.

#### The test matrix

[`scripts/jit-test-matrix.sh`](../../../../../scripts/jit-test-matrix.sh) runs the rows below on `jit-tests.md`, each on its own copy of the transcript, and reports a row as passed when the transcript completed, the output equals the input, and the log shows the JIT in the state the row asks for (compiling, or off). `--opt` and `--debug` select the optimized and debug-RTS trees, `--list` prints the rows, and row names run a subset. Logs of failed rows are kept. All on `jit-tests.md`, output identical each time. The stress modes: `poll=N` fires the preemption poll every N entries; `ustack=N` starts the Unison stack with N slots; `cstack=N` sets the C stack budget to N bytes; `callee=N` treats every N-th callee as not compiled; `alloc=N` makes the allocation budget N words; `gc=N` runs a minor GC after every Nth return from native code, so that a store the write barrier missed is caught by the debug RTS at the next return (the proof of the 2026-11-04 low-water mark: `jit-tests.md` under `eager` with `gc=1` on the debug RTS fails without it and passes with it); `pool=N` makes the constant pool's first array N entries so that it grows and functions check its size; `install=N` sleeps N ms before each function of a module is installed; `lists=N`, `texts=N`, `bytes=N` run N random operations through the C helpers at startup, each on the results of earlier ones, checking every result's structure and elements against Haskell.

| Configuration | Exercises |
| --- | --- |
| `UNISON_JIT=off`; `eager`; `on`; `on` with `UNISON_JIT_THRESHOLD=1` | the three modes; with threshold 1 (eager's default) every re-entry point is generated on first use |
| `eager` with `UNISON_JIT_STRESS=` each of `poll=3`, `ustack=4`, `cstack=2048`, `callee=3`, `alloc=64` | each exit path on its own |
| `on` with `THRESHOLD=1` and `poll=3` | the poll interrupting Lets whose bodies aren't compiled yet: the cap on ad hoc re-entry functions (`UNISON_JIT_REENTRY_ADHOC`); the stats line "ad hoc exits" shows it working |
| `eager` with `UNISON_JIT_STRESS=callee=2,cstack=4096,poll=5,ustack=4,alloc=64,pool=8` | all of them together ("the combination") |
| `on`, `THRESHOLD=1`, `install=5`, alone and with the combination | code installed while the program runs |
| the stress runs with `UNISON_JIT_EXIT_COST=0 UNISON_JIT_ENTRY_COST=0` | the estimate doesn't hide code from the tests |
| `UNISON_JIT_DISABLE=worker` | the uniform form everywhere |
| `UNISON_JIT_DISABLE=xcall` | calls between modules through the uniform entry only, no register entry |
| `UNISON_JIT_DISABLE=nmbarrier` (only under `+RTS -xn`, and only with `UNISON_JIT_DEBUG=1`, which every `DISABLE` needs) | the non-moving collector's write barrier left out, in generated code and in the C helpers: the control for `transcripts-manual/jit-nonmoving.md`, which must then fail |
| `UNISON_JIT_DISABLE=list,text,bytes,name` | the fallback paths of the C helpers |
| `UNISON_JIT_DISABLE=irhelpers`, `=requests`, `=records`, each under the combination | the C copies of the IR helpers; every request exits; every record instruction exits |
| `eager` with `UNISON_JIT_STRESS=lists=20000,texts=20000,bytes=200000` | the helper self-tests; after touching either side of a helper, run a few hundred thousand steps, on the debug RTS too (in `on` mode the checks run on the compile thread and may not finish before a short transcript does; use `eager`) |
| on the debug RTS with `-DS`: `on` with `THRESHOLD=1`; `eager`; `on` with `THRESHOLD=2`, both costs 0 and `install=5,pool=8,alloc=64,poll=7`; and `jit-benchmarks.md` with `on` and `THRESHOLD=1` | heap sanity under each |
| the first few rows on the optimized build | some failures only exist at `-O2`, and the startup checks can fail closed there for reasons the fast build never shows (a sample list GHC floated to a top-level constant) |

#### What else counts as a test

- [`scripts/jit-limits.sh`](../../../../../scripts/jit-limits.sh): the programs whose right outcome is the process ending in a controlled way, which a transcript can't record. Today these are allocation sizes no heap can hold (`IO.bytearray 9223372036854775807` and the like), where both the interpreter and native code must end with GHC's heap-overflow exit (251), never with a signal: the C helpers that size an object from a program's number allocate through `allocateMightFail` and hand a refusal back to the interpreter (`nat_alloc_mayfail` in `jit_builtins.h`, 2026-10-24), where `allocate()` would have exited from inside the helper and the pinned path once dereferenced a null result. Run it with the JIT off and eager after touching an allocator.
- The "Bounds and limits" section at the end of `jit-tests.md` (2026-10-24): offsets that wrap when a length is added to them, a closure with many captured variables called from deep frames while the stack grows, and a non-tail call nested in a dozen inline bindings. They are ordinary rows of the matrix; the `ustack` and `cstack` stress rows are the ones that make them bite.
- `runtime-tests`' `mcode.malformed` (`--ta mcode.malformed`): ANF and values a typechecked program never produces, which the emitter and the value decoder refuse before building anything from them (2026-10-25): a record literal of the wrong arity, a let naming more values than its binding yields, a function body yielding two values, an unboxed sum match away from its primitive, a decoded record with too few values, a decoded partial application with too many arguments. These are the properties of code that native code relies on without checking at run time ([`resultCount`](../MCode.hs#:~:text=resultCount%20%3A%3A), [`recordArity`](../MCode.hs#:~:text=recordArity%20%3A%3A), [`sumFields`](../MCode.hs#:~:text=sumFields%20%3A%3A), the two `goV`s in [`Machine.hs`](../Machine.hs#:~:text=reifyValue0%20%3A%3A)); everything else native code reads about a value, it reads from the value.
- The "Field counts come from the object" section at the end of `jit-tests.md` (2026-10-24): `Any.unsafeExtract` hands a wide match a value of another type with the same shape (taken apart as this type's), and values with fewer and with more fields than the arm binds (a runtime error from the interpreter's `dataBranch`, which runs an arm only when the object has the arm's count); native code exits to the interpreter at the match on every mismatch (`requireWide`, the whole-tag compare), so the two modes agree.
- `runtime-tests`' `Foreign.Arrays` (`stack test unison-runtime:runtime-tests --fast --ta Foreign.Arrays`): the checks only ill-typed code reaches, such as `PinnedByteArray.contents` on an array that isn't pinned (the type says pinned; the run-time object doesn't).
- The benchmark transcript, with the fast binary: base library code has shapes the builtins-only tests don't (a `Let` inside an inline binding was found by `printTime`, not by the tests).
- The rope library's own tests and benchmarks: `stack build --fast --test unison-util-rope` compares the Deque with `Data.Sequence` and the rope with a string model, checking the structures' invariants (`valid`) after every step; `stack build --work-dir .stack-work-opt --bench unison-util-rope` runs the benchmarks (`--ba "--csv FILE"` for the numbers).
- The interpreter's own speed: re-measure `off` whenever [`enter`](../Machine.hs#:~:text=enter%20%3A%3A), [`apply`](../Machine.hs#:~:text=apply%20%3A%3A) or [`yield`](../Machine.hs#:~:text=yield%20%3A%3A) change. The hot-count test is on the path of every call, and a version that compared with a configured threshold made the interpreter 5 to 20% slower with the JIT off.

#### Pitfalls

- **A matching transcript says nothing about whether the JIT was on; the log does.** Run with `UNISON_JIT_LOG=1` and look for "the JIT is off" and for the compile lines. When a run's numbers look like the other mode's, count the "JIT is off" lines before reading the table. A check script has to count them too, not only grep for "error": a startup self-test that fails says "the JIT is off" and nothing else, and on 2026-11-05 `jit-tests.md` under `eager` passed on the interpreter that way, after a change to `compareClosure` that the universal-comparison self-test had caught.
- **In on mode a one-shot evaluation may never run natively.** With `UNISON_JIT_THRESHOLD=1` the compile runs on its own thread, and a watch expression that evaluates once is usually done in the interpreter before the module is ready, so a new test section's code only runs natively in a later stanza if at all, and a dump directory stays empty. To see the IR a section generates, run it under `UNISON_JIT=eager`.
- **A segfault after "Completed transcript" is the compile thread.** Seen once (2026-10-29, `UNISON_JIT=on UNISON_JIT_THRESHOLD=1` with the IR dump, the test transcript; crash report `unison-2026-10-29-073818.ips`): the main thread finished and the process began to exit while the compile thread was inside LLVM's code generation for the last stanza's module (`SelectionDAGISel` on `ghc_worker`), and the teardown pulled memory from under it. The transcript's output was complete and matched. Fixed on 2026-11-03 after CI hit it in the merge queue: `jitShutdown` stops the compile thread and waits for a compile in flight before ucm exits (design.md, "The pieces").
- **Check the executable is the one you think.** When `stack build` fails in the runtime, `stack exec unison` still runs the last executable that built, whose probes describe the old layout.
- **Check the run finished.** A run that dies (an `LLVM ERROR` at module compile, say) leaves the previous `.output.md` in place, and a diff against it passes by accident. Delete the output file before the run, or look for "Completed transcript" in the log.
- **A startup probe's sample values are built in an unoptimized module** ([`Layout.hs`](Layout.hs) under `--fast`), so a `Val`'s type tag bound by `let` is an untagged CAF pointer, a list literal's elements and a `fst` are thunks, and `writeArray arr i . any'` stores a thunk of the coercion; the C side then reports "untagged value" or a failed layout check. Build samples through the `-O2` modules' constructors (`NatVal`, `recordVals . segFromList`, `formData`) and write `evaluate (any' v) >>= writeArray arr i`, as the existing probes do.
- **A pointer tag written as a literal in C is a layout assumption the probes don't check.** When `GPAp` moved past the sixth constructor every data tag changed; the generator took the new tags from the layouts, but six C builders tagged their results with literals, and the list self-check caught it ("splitting a list of 0 elements differs from the interpreter") and turned the JIT off. The tags C writes now arrive from the inits (`LF.data1_tag`, `LF.data2_tag`, `PF_pap_tag`); keep it that way.
- **`LLVM ERROR: Instruction Combining on <helper> did not reach a fixpoint`** at a module compile is LLVM's self-check on the combiner, fatal in the LLVM in use, and it means the helper's IR got harder to optimize, not that the pipeline is wrong: the hash walker with a loop over a dynamic field count inlined into `mh_val` did it, and cost the hash row 40% besides; straight-line code for the common shapes with the loop out of line (`mh_data_wide`) fixed both. `instcombine<no-verify-fixpoint>` in `UNISON_JIT_PASSES` turns the check off if it is ever needed to get a run through.
- **Per-thread state made before the settings are read is a trap:** the self-tests once created the thread's JIT context before the stress settings were configured, and on that thread the stress poll fired on every entry forever. Under the stress modes the C entry now reports a function that leaves with the same exit a million times in a row without moving the stack.
- **`ret` into the Haskell heap with `fp` a small integer is a C stack pointer off by one argument pair.** The crash of 2026-11-05 (one benchmark run in sixteen under `on`, the reports in `~/Library/Logs/DiagnosticReports`): `pc == lr`, both a heap address ending in `018` (the boxed stack's payload, which a `MutableArray` large object puts 24 bytes past a block boundary), `fp` 6912, and x0..x4 a padded OK result, so a function had just returned normally and the *caller's* `ldp x29, x30` read the spill pair below the real one. Cause: on arm64 a `tailcc` worker with more than three argument pairs pops its stack arguments in its epilogue (callee cleanup), and LLVM's shrink wrapping let the frameless early-return path skip the epilogue and the pop, so the caller's `sub sp, #16` after the call left its stack pointer low; it needs a worker *entered* by a real call with its first test already true, which in a loop happens when an exit lands on the last iteration and the re-entry function calls the worker again. The fix is `-enable-shrink-wrap=false` in `jit_llvm.c`; the test is the last section of `jit-tests.md` under the `callee` and `poll` stress rows, which crash in seconds on the bug. The way there: list the shapes that write a word and pointer pair over the C stack, dump the IR (`UNISON_JIT_DUMP_IR`), compile the module with `llc -mtriple=arm64-apple-macosx -O2 -mcpu=apple-m1` and read the prologue, epilogue and every `ret`. Core dumps are off on this machine for every process (a deliberate segfault leaves `/cores` empty), so reproduce under `lldb --batch -o run -k ...`. `script -q file cmd < /dev/null` gives ucm a terminal, which line-buffers stdout so the row a crash lands in is in the file, and returns the signal number (10 for a bus error) rather than 128 + it; set `UNISON_PAGER=cat`, or ucm pages its output and waits for a key.
- **A row that is slower than trunk's JIT by half is an exit per iteration, and `UNISON_JIT_STATS=each` on the row alone names the site in one run.** The library suite's `Remote.Ref` row (0.58x of trunk, 2026-11-05) was 10,000 `resume` exits at one `App (Env f)`: a known function applied to fewer arguments than it takes, after a `Box` of a wide variable it captures, a shape the Let case of the code generator didn't match (it covered a binding that *is* the application) and `genApp` didn't handle at all; trunk has no boxes, so there the binding was bare and built in place. The MCode printer hides `App`'s first field (the known-convention flag), and the dump needs `UNISON_JIT_DEBUG=1`. When a new path yields a value with an exit for pending arguments, the exit's resume section must read the value from where the yield left it: the first version resumed at the application one slot down and a forced thunk came back as `do (3, 3)`; `jit-tests.md` under `eager` against `off` is what caught it, so diff the three modes' outputs, not only the mode the proof runs.
- **The merge queue drops a pull request without a comment when the full run outlasts its 60-minute check timeout, and the jit jobs are what grow.** PR 6330's second full run (2026-11-06) passed every job but took 2 h 15 min, and the pull request was removed from the queue at 05:35Z with no failure comment (the bot comments only on a failed run); the earlier comment was the Windows failure. Compare the jit jobs' step times against an earlier merge-queue run (`gh run view <id> --json jobs`); the per-module compile lines of `UNISON_JIT_LOG=1` say whether it is more modules or bigger ones (that day: the same 43-function module at 95 MB of IR instead of 31, since eager generated every `Let` body, each the function's whole suffix, and the wide convention doubled each suffix). Reproduce on the optimized build with the trunk worktree's binary beside the branch's, then try the switches (`UNISON_OPTIMIZATIONS=-wide`, `none`, `UNISON_JIT_DISABLE=xcall`) before reading IR.
- **A crash in the GC** is usually a bad object native code built or a pointer it stored untagged, or a store the write barrier missed. The debug RTS puts the fault near its cause, and its message says which: an info pointer of `0xaaaaaaaaaaaaaaaa` is the pattern it fills freed memory with, so the object was collected while still referenced, which is a missed barrier (2026-11-04: the cards below the entered frame, written by a re-entry inside an inline binding, were never marked; one run in several of the benchmark suite under `on`, never under `eager`, since re-entries are what `on` does). A run that crashes only under `on` and only sometimes is a GC-timing bug, and the debug RTS under `on` with `THRESHOLD=1` and `UNISON_JIT_STRESS=gc=1` is the way to make it show every time. The 2026-11-05 one was a heap object kept in a C static (design.md, "The constant pool"): three days of stack scans found nothing because the dead pointer entered through a helper's argument, and the statics check (`unison_jit_check_statics`) found it in four minutes. Check the statics first. The debug RTS over the optimized build puts the fault near its cause; macOS's crash reports (`~/Library/Logs/DiagnosticReports`) show which thread was where at exit time; `lldb` in batch mode needs `--source-on-crash` with the RTS's timer signals passed (`process handle SIGALRM SIGVTALRM SIGUSR2 -s false -n false -p true`), `PAGER=cat` and stdin closed, else it stalls on a prompt. A laziness leak on the compile thread shows in `+RTS -hT` as `:` cells.

**A control that passes may be no control.** The first stress for the non-moving barrier passed its control for three reasons, found one at a time over an afternoon: `UNISON_JIT_DISABLE` is read only under `UNISON_JIT_DEBUG=1` (so every "control" run had the barrier on; the IR dump, run with the debug variable, showed no pushes and hid that); it moved values in one direction only (the marker visits the arrays in a fixed order, so a move from the first-visited array to the other loses nothing); and the debug RTS's `-DS` doesn't see the loss, since a swept object keeps its bytes until its block is reused and a pointer to it still looks valid. The stress that works swaps both ways, keeps promoting fresh objects so that freed blocks are reused, and sums the arrays at the end; the real control then crashes in the marker, or prints a wrong checksum, in seconds on the optimized build, three runs out of three. Before any control is believed, make it fail once: here, the binary built before the barrier failed the library suite under `+RTS -xn` in two runs out of two, which was the first real evidence. And a new store sequence must be run under `UNISON_JIT_DEBUG=1` first, under every collector it is generated for and under the default one too: the barrier's branch gave a phi in `copyCaptured` a predecessor it didn't name, which the verifier reports and an unverified build runs as an infinite loop; and the first cas push treated a pointer register as an integer, invalid IR the verifier reports and an unverified build answers by rejecting the module, so the row ran interpreted at 0.12x, which only the benchmark noticed.

#### Logs and statistics

- `UNISON_JIT_LOG=1`: the compile log (per module: functions, compile time, IR size, and the time split into generating the IR, LLVM's parse and optimization, and LLVM's code generation), why a combinator or part of one was left to the interpreter ("partly interpreted"), the startup checks and how long they took, the thread's C stack size, and "the JIT is off" with the reason when a check failed.
- `UNISON_JIT_STATS=1` prints exit counts per site after each evaluation, with the compile totals first (modules, functions, auxiliary functions, re-entry functions generated on demand and never asked for, IR size, time), then the ad hoc exits (re-entry functions asked for because of the poll or stack growth, and exits that found their definition at the cap `UNISON_JIT_REENTRY_ADHOC`) and how often the trampoline entered each native function; `UNISON_JIT_STATS=each` prints the exits taken since the program last wrote output, after each write, which gives per-benchmark exits for a suite that prints a line per benchmark; `UNISON_JIT_STATS_EVERY=N` also prints every N exits, for evaluations that never finish. A run with statistics is at most 7% slower on the entries that exit most; quote timings from runs without them. The counts for "depth 1000000" are the quickest way to see whether frames are unwinding more than they should.

#### Dumps

- `--jit-dump-ir DIR` (or `UNISON_JIT_DUMP_IR=DIR`) writes one `.ll` file per module into `DIR`, with the MCode of each function as a comment above its IR and a line for each combinator that wasn't compiled and why; `-` prints to stderr. Two versions of each module are written: `unison_<n>.ll` is the text handed to LLVM and `unison_<n>.opt.ll` the module after the optimization passes, which is what runs. For the arm64 assembly: `/opt/homebrew/opt/llvm/bin/llc -O2 unison_<n>.opt.ll -o out.s`. For example: `stack exec unison -- --jit eager --jit-dump-ir - transcript.fork t.md 2> t.ll`. Two dumps from different binaries differ in the info-pointer addresses baked into the IR; mask runs of ten or more digits before comparing them.
- `UNISON_JIT_DUMP_MCODE=1` dumps the MCode as it is loaded. To look at a site named in the statistics (`CIx ... <group> <n>`): run with `UNISON_JIT=off` and this, kill it once loading is done, and search the dump for `<group>:<n>:`.

#### LLVM knobs

- `UNISON_JIT_PASSES` is the LLVM pipeline a module is optimized with (the default is [`defaultPasses`](Config.hs#:~:text=defaultPasses%20%3A%3A), the parts of `default<O2>` our code uses, [2026-10-09 pipeline](benchmarks/2026-10-09-pipeline.md); `default<O2>` for comparison; empty runs none) and `UNISON_JIT_CODEGEN_LEVEL` (0 to 3) the level of the JIT's target machine, for measuring what the optimizer and the backend cost and buy ([2026-10-09 O0](benchmarks/2026-10-09-o0.md)); full O0 with workers crashes, see there.
- `UNISON_JIT_INLINE_THRESHOLD=N` sets LLVM's inliner threshold (default 225), for measurement; `UNISON_JIT_SCHED` (any value) keeps LLVM's machine schedulers on (off by default, [2026-10-09 compile time](benchmarks/2026-10-09-compile-time.md)); `UNISON_JIT_LLVM_OPTS` is any further LLVM command line options, space separated. All go through `LLVMParseCommandLineOptions` at startup, in `jit_llvm.c`. To see where the backend's time goes, sample the harness: [2026-10-10 backend profile](benchmarks/2026-10-10-backend-profile.md).

#### Traces and switches

Every switch below, the stress modes, the dumps, `UNISON_JIT_PASSES` and the LLVM options are read only when `UNISON_JIT_DEBUG` is set (JIT.Config's `readConfig`, `debug_getenv` in `jit_llvm.c` and `jit_rt.c`): the test matrix sets it, `--jit-dump-ir` sets it, and a shell that wants them sets it once. Without it they are ignored, so that a program's user can't be handed a weaker runtime by a variable in the environment (security review, 2026-10-24).

- A module is generated once for real (after repetitions that only settle which functions are workers): the exit and frame indices and the auxiliary cells in the generated text are placeholders relative to the function, patched once the tables are sized from that generation's own counts (`patchIndices`, `relocateCells`). Before 2026-10-28 a separate counting pass sized the tables, and when it disagreed with the real pass (a unit failing in one and not the other) every later function's exit indices were off by one against its IR: a resume became a re-enter, and the function re-entered itself forever. Anything that makes the table layout depend on a second generation is a bug of that family.
- `UNISON_JIT_TRACE=1` describes every exit taken (`describeExit`), prints each re-entry with its cell, and the C side reports an exit taken a thousand times in a row by the same function, with the C stack, the budget and HpLim as it saw them (2026-10-28). The on-mode hang of that day was read off this: a function re-entering itself through an exit registered under the wrong index.
- For a backtrace of Haskell code under `lldb`, the executable needs its symbols: `stack build --fast --no-strip`. That flag changes the snapshot, so the executable lands in a different `.stack-work/install/.../bin` and `stack exec unison` keeps running the old one; run the new binary by its path (the newest `bin/unison` under `.stack-work/install`). Found out after three test loops had run the stale binary (2026-10-28).
- A run that makes no progress is not necessarily hung: a stanza of the test transcript takes minutes under a stress mode, with the JIT off (158 s for the first eleven stanzas), or under a context-switch interval made tiny with `+RTS -C`, which only slows everything down. Judge a hang by the progress line staying put for several minutes, then attach `lldb -p` (allowed on this machine since 2026-10-28) rather than `sample`, which never returned on a hung process.
- `UNISON_JIT_TRACE=1` prints every native entry and exit, on both the C and Haskell sides. Unusable on programs that load base (it exhausts memory during the load); fine on the test transcript. `UNISON_JIT_TRACE_YIELD=1` prints each value native code yields, its pointer tag and closure type with its fields two levels down; cheap, and what found the untagged-pointer crash. `UNISON_JIT_TRACE_TEST=1` prints each startup self-test operation as it runs, for finding one that crashes.
- `UNISON_JIT_EXITS=blocks` makes exits and unwinds write the frame back through generated blocks instead of the one call per site to `unison_jit_exit_frame` that is the default ([Write-back](design.md#write-back); [2026-10-09 exit call](benchmarks/2026-10-09-exit-call.md)). For comparison, and the fallback should the call form misbehave somewhere.
- `UNISON_JIT_BUMP=0` makes every allocation call `allocate` instead of bumping inline, for comparison.
- A continuation that misbehaves after a serialize-load round trip: the interpreter has no trace of its own for frames, so add a temporary one that prints the frame at each leap in `yield` (`Push` with its sizes and `CombIx`, `Mark` with its handlers), `jump`'s pending-argument count and segment size, and reflection's slot counts, and compare a direct run's trace with the loaded run's; the first line that differs names the stage at fault (this found the pending-argument count of loaded continuations, 2026-11-01).
- `UNISON_JIT_DISABLE=...` turns features off one at a time; the list is in [`Config.hs`](Config.hs#:~:text=disabled%20%3A%3A). Bisecting with it is how the exponential generator and the pool's lazy segment boxes were found.
- **`emitSection: a let of N names whose binding yields M values`** (or `emitComb: a function body that yields ...`, `an unboxed sum match ...`, `a record literal of ...`) at load is the emitter refusing ANF it cannot lay a frame out for ([`resultCount`](../MCode.hs#:~:text=resultCount%20%3A%3A)). From a codebase this means the ANF conversion or a builtin changed shape, not that the program is wrong: a primitive that pushes other than one value has to be bound by a direct let of exactly that many names, or, for the two unboxed sums (`LOAD`, `TFRC`), by a direct let of the tag whose body is the sum match ([`sumFields`](../MCode.hs#:~:text=sumFields%20%3A%3A)). Both rules apply with the JIT off too, so a false refusal shows up in every mode, and the message prints the term.

#### Measuring

- **Benchmarking rules.** `suite` is the test of whether the JIT is usable on library code; `jitSuite` is the test of whether it is fast. Measure both, on the optimized build, on an idle machine, never while another job is running. One run of `suite` is not evidence for a 20% change in a 20 ms benchmark; its run-to-run noise is about 5% both ways, and its `Remote.Ref` row is a single run of 20 ms early in the suite that measures where a major GC lands, not the code. The first benchmark's label in the console output is overwritten by the transcript's progress line, so the first timing appears without a label. Record a run as a file in [benchmarks/](benchmarks/) named `<yyyy-mm-dd>-<what-it-measured>.md`: what the run was (build, mode, how many runs, which commit if it matters), the table, then what it showed. The [latest full run of both suites](benchmarks/2026-10-05-every-benchmark-end-of-m7.md) is what the next full one gets compared against; the later files measure one change each.
- **Counting what the interpreter dispatches on:** a `MutablePrimArray` indexed by `base + dataToTag# x` (the `DataToTag` class in `GHC.Exts`), bumped at the top of `eval`, in the `Ins` case and wherever a closure is scrutinized, and a thread that writes it to a file once a second; the indices map back to names through the declaration order. Two hooks and a rebuild of the optimized tree; what chose the constructor orders ([2026-10-15 constructor order](benchmarks/2026-10-15-constructor-order.md)).
- **Profiling the trampoline:** run the transcript in the background, `sample <pid> 5`, and resolve the addresses in the `unison` binary against `nm -n`. Haskell code shows up as offsets from the nearest exported symbol, which is coarse, but the C and runtime functions are named, and those were most of the waste when the round trip was cut in half.
