# Exits as one call per site (2026-10-09, finished 2026-10-10)

After the [write-back](2026-10-09-write-back.md) work, the shared write-back blocks were
still three quarters of the IR of the suite's largest module: 193 blocks for 204 sites, about
15 live slots each, six lines a slot. This replaces the blocks with one call per site to a C
routine, `unison_jit_exit_frame`, that takes the live slots as variadic arguments and a
constant descriptor saying where they go ([Write-back](../design.md#write-back)).
Suite, optimized build, `--jit on`, `UNISON_JIT_STATS=1`; three or four runs each;
`UNISON_JIT_EXITS=blocks` is the earlier form.

## Why not `llvm.experimental.deoptimize`

The plan was the deoptimize intrinsic with stack maps, which records where the operands are
instead of spilling them. A hand-written module through `llc` settled it: LLVM lowers the
call as one that never returns (a `brk` follows it), so the runtime routine `__llvm_deoptimize`
must pop the enclosing frame and restore its callee-saved registers itself, and the stack
map says the frame's size but not where those registers are. That is assembly per platform.
A `gc.statepoint` returns normally and gives the same stack map, but its site is the same
machine code as the varargs call (the deopt operands are spilled to stack slots by default,
`use-registers-for-deopt-values` is off), plus a `gc` attribute on every function and a table
to parse and index by return address. The varargs call is plain C everywhere.

## Two things the first version got wrong

- **The routine returned the status.** Then the status at the site was no longer a constant,
  the function lost its `range` return attribute, and a caller that had folded its checks of
  the callee's status (the "callee first reached once the caller is hot" row, 118 → 183 µs)
  no longer could. The routine returns nothing and the site returns its constant.
- **The C calling convention.** A callee's exit inlined into its caller is followed by the
  caller's unwind: two calls in a row, with the caller's live values live across the first.
  Those went to callee-saved registers, and the whole hot function paid to save eight of them
  at every entry (Collatz 69 → 72 µs, murmur 251 → 262 µs; the blocks form had no calls at
  all in these workers). The routine now has the `preserve_most` convention on both sides
  (`__attribute__((preserve_most))` in C, `preserve_mostcc` in the IR): the callee preserves
  every register but x0–x8 and x16–x18, and the sites keep their values in scratch registers.
  GCC has no such attribute; Linux is skipped for now, so the C file refuses to build there
  with a pointer here.

Binary tree lookups and Collatz are faster because their hot workers no longer save
callee-saved registers at entry (the write-back blocks kept values in them for the exit
paths; a `preserve_most` call doesn't). Bytes drop and Text uncons vary by ±5% between runs
of either mode. Murmur is 3% slower because its worker (`u612_0_w`, 16 sites) is no longer
inlined into its callers: the inliner's cost for it went from 130 to 240 against a threshold
of 225, each site being a call it charges for where a branch to a shared block was free.
See the inline threshold below.

## The inline threshold

`UNISON_JIT_INLINE_THRESHOLD=N` (new, `jit_llvm.c`, LLVM's `-inline-threshold`; the default
is 225) raises the inliner's threshold. At 300 the murmur worker is inlined again and the row
is back where it was; the other rows and the IR size don't move, and the compile time is
within the noise of two runs. Left at LLVM's default for now: a global inliner setting
affects every module, and one row at 3% isn't enough to decide it on. Rows that moved, median
of the runs, relative to blocks:
