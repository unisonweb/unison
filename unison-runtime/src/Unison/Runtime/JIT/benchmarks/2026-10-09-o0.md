# What the optimizer and the backend are worth (2026-10-09)

How much of a module's compile time is LLVM's optimization passes, how much its code
generator, and what each buys at run time. Optimized build, `--jit on`, the suite. Two new
settings exist for this, both defaulting to today's behaviour: `UNISON_JIT_PASSES` (the
pipeline; empty runs none) and `UNISON_JIT_CODEGEN_LEVEL` (0 to 3, the level of the JIT's
target machine; the code generator's O0 is fast instruction selection and the fast register
allocator).

## Per module, in-process

A C harness driving `jit_llvm.c` on dumped modules (so no process start-up in the numbers),
the suite's 560 KB module, median of 5 after a warm-up; the 37 KB and 94 KB modules split
the same way within a few percent:

| configuration | parse + passes | code generation + link | total |
| --- | --- | --- | --- |
| today: `O2`, backend default | 77 ms | 61 ms | 138 ms |
| `O2`, backend O0 | 77 ms | 14 ms | 91 ms |
| no passes, backend default | 6 ms | 77 ms | 82 ms |
| full O0 | 6 ms | 17 ms | 23 ms |

So the `O2` passes are about half of today's time, the backend at its default level a bit
under half, the parse 4%. The fixed cost per module is about 2 ms (0.6 ms of it building the
`O2` pipeline), 10% over the suite's 69 modules. Full O0 compiles six times faster.

Full O0 with workers crashes in generated code (a load through the value 0x2e, in a module
of three functions; `O2` output at backend O0 runs, no passes at backend O1 runs, and
`mem2reg` alone at backend O0 crashes), so it is the fast instruction selector on our
unoptimized worker code (`tailcc`, `musttail` between different signatures) that goes wrong,
in LLVM or in what we feed it. Not chased: it is not a configuration that would ship, and
the question was the cost split.

## Takeaways

Both halves matter, and about equally: without the passes the loops are 6 to 7 times slower
(`sumTo`, the two cross-definition rows), and with the backend at O0 they are 5 to 9 times
slower even from `O2` output, since every value then lives in a stack slot. The rows that
don't move are the ones whose time is in the C helpers (text, bytes, byte arrays). Backend O1
is the default backend in all but name for us (the schedulers are already off).

For a tiered design this says: a first tier at O0 compiles six times faster but runs several
times slower than the second tier, so it only pays where the interpreter is slower still
(it is, by a larger factor on these loops), and the second tier must follow quickly. A
cheaper middle ground is a lighter pipeline that keeps `mem2reg`, `instcombine`,
`simplifycfg`, `gvn` and the inliner, measured in the harness at a quarter of `O2`'s cost;
whether it keeps the code quality is the next thing to measure
([optimization-ideas](../optimization-ideas.md#compile-time)).
