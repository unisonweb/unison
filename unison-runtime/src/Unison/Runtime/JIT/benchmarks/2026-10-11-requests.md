# 2026-10-11: ability requests of affine handlers

Requests of affine handlers run natively: the request finds the handler in the environment
and calls it like a function value, and the handler's case (a request match, the state
update into the handler's ref, the return to the requester) is generated too. "Ability
requests" in internals.md. Optimized build, `UNISON_JIT=on`; the suite runs with
`UNISON_JIT_STATS=1` (compare.py keys on its compile summary), medians of three; the
interpreter column is one run.

Three rows added to the suite for this: a `Counter` loop of requests without fields, a
`Store` loop of a `get` in a let and a `put` with a field then a `get` in tail position,
and a `handle` installed on every iteration around two requests.

| | interpreter | JIT, before | JIT, requests | |
| --- | --- | --- | --- | --- |
| Counter: 100000 requests | 16.5 ms | 16.2 ms | 3.81 ms | −77% |
| Store: get and put, 100000 iterations | 26.8 ms | 32.8 ms | 9.44 ms | −71% |
| handle installed per iteration, 10000 iterations | 6.28 ms | 6.26 ms | 6.25 ms | 0% |

"Before" is the same rows measured standalone on commit f2fe3a5fe (`UNISON_JIT_STATS` off),
where native code gained nothing on requests and lost on Store: each request was an exit,
the interpreter resolving and applying the handler and running the five matcher
instructions, then a re-entry. Standalone and without statistics, the new numbers are
Counter 3.48 ms (35 ns per request against 160), Store 6.53 ms and handle 4.46 ms (−29%): the
`handle` row's gain depends on what `on` mode has compiled when the loop runs, and the
`Reset` of each iteration is still the interpreter's (optimization-ideas.md, "`handle`
itself").

Exits: a request loop of 300000 requests takes none but the poll's; the first `SetAff` of
each handler instance took a call-out until the interpreter's `extendPAp` was made to store
its captured value strictly.

The other rows are unchanged within noise (Text and Bytes drop 1 −5% and −9%, within their
usual spread). Compile totals on the suite: 71 → 86 modules, 94 → 117 functions, since
functions that make requests now pass the exit rule; the compile time went 880–1046 → 1047–1081
ms with them (parse and optimize 267–283 → 329–343, code 524–535 → 616–628).
