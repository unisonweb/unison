# 2026-10-19: the C runtime in one file per family

Review of the PR asked for `cbits/jit_rt.c` (4,113 lines) to be split: the machinery in one
file, the native builtins in one file per family. The split was made twice, and this run is
what decided between the two.

*Separate translation units*: each `jit_builtins_<family>.c` compiled on its own, with what
the files share (allocation, the small constructors, the list structure's internals that the
ropes use, `parray_new` that records use) as hidden-visibility globals declared in a shared
header, the inline ones defined there. *One translation unit*: the same files, but included by
`jit_rt.c` the way it already includes `jit_helpers.c`, so that everything shared stays
`static` and inlinable as it was in one file.

Optimized build (`.stack-work-opt`), `--jit on`, `jit-benchmarks.md` through
`transcript.fork`, against the "hoisted" column of
[2026-10-19 JIT handle](2026-10-19-jit-handle.md), the run just before the split (same
machine). One run per column, a second run of each agreed.

As separate units three rows lost 4 to 7% in both runs: text append (198 → 207 µs), bytes
drop (1.79 → 1.93 ms) and the record literal row (7.4 → 7.9 ms). Those are the rows whose
helpers cross from the ropes into the list structure's internals and from records into the
array allocator: in one file clang inlines those calls, across files they are calls. As one
translation unit every row is back within noise of before, so that is what is kept: the
files are for reading, the compiler sees one unit. (Link-time optimization would recover it
too, but would have to work with GHC's link step on five platforms; not tried.) The cost of
the unity build is that an edit to a family file alone does not recompile `jit_rt.c`
(development.md says what to do: `touch` it).
