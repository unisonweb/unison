# 2026-10-10: byte array reads in the generator; murmur as an IR module

Two changes to how generated code reaches the data-structure helpers, both from
[helpers-in-ir-plan](../helpers-in-ir-plan.local.md) (local) and documented in
[design.md](../design.md#the-ir-helpers), "The IR helpers":

1. `MutableByteArray`/`ImmutableByteArray` `size`, the reads of every width and byte order,
   and the writes are generated inline (`byteArray`, `byteArrayElem` in `Codegen.hs`) instead
   of calling `unison_jit_barray_size`/`_read`/`_write`. The three C helpers are deleted.
2. `unison_jit_murmur` is compiled from C to LLVM IR (`cbits/jit_helpers.ll`, embedded) and
   added to the JIT as a module at startup, so generated code calls a function LLVM compiled
   for the same target. The C copy stays for the startup self-check and
   `UNISON_JIT_DISABLE=irhelpers`.

The motive for both was the two-word `{ i64, i64 }` return these helpers share: C and
generated code agree on it on arm64 and System V x86-64 but not on Windows x64. After the
change no C helper returns a pair.

Optimized build, `UNISON_JIT=on UNISON_JIT_STATS=1`, the suite in `jit-benchmarks.md`, two
baseline runs (commit 03d8acef8) against three runs of the change. Medians.

## Observations

- **The byte array row: 4.18 ms → 0.49 ms (−88%).** The loop does 4 writes and 6 reads at
  constant offsets of one array. In the optimized IR of its module, no helper calls remain;
  5 loads and 4 stores at byte alignment with the byte swaps, and 2 `icmp ugt` where the
  checks were 20: LLVM merged the bounds checks of the ten operations on the same array into
  the dominating ones, and forwarded the 64-bit value stored at offset 8 straight to the read
  of the same offset, which is why there are five loads for six reads.
- **Murmur: unchanged (−2%, noise).** Expected: the call is still a call; only who compiled
  the callee changed. The module costs about 55 ms once at startup (about 30 ms to parse and
  optimize its 950 lines, 25 ms to compile them; `UNISON_JIT_LOG=1` reports both as
  "IR helpers"), nothing per call.
- **The other rows are within ±4%**, the suite's run-to-run spread (Collatz's three runs
  were 66.6, 66.6 and 69.7 µs against a 66.5 baseline). Compile time is unchanged.
- **A wrong turn, measured.** The first version of the IR module exported the runtime's
  layout tables (`LF`, `TK`, `BK`, `AK`, `HK`) as ordinary globals so that the module could
  refer to them by name. That made every C helper address them through the global offset
  table (486 GOT loads in `jit_rt.c`'s assembly where there had been 1209 direct page
  references), an extra dependent load per helper, and the rope rows paid for it: Bytes
  append +6% in all three runs (242, 248, 235 µs). Keeping the tables `static` and defining
  their names as absolute symbols in the JIT before the module is added put the rows back on
  the baseline (230, 231, 227 µs).

## What the IR looks like

`cbits/jit_helpers.ll` after `gen-helpers.py`: 947 lines; the five tables as `external
global`, the four functions it calls (`unison_jit_settle`, `rope_chunk_at`, `lv_each`,
`murmur_fail`) as declarations, five attribute groups holding only `nounwind`,
`willreturn` and `memory(...)`, no target lines, no metadata. `gen-helpers.sh --check`
confirms it matches its source.
