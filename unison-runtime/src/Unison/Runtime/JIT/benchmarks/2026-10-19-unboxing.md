# 2026-10-19: the hand-unboxed code measured

Review of the PR asked whether the manual unboxing in the rope code (`Unison.Util.Rope`,
`Unison.Util.Deque.Internal`, `Unison.Util.Text`, `Unison.Util.Bytes`: functions returning
`(# Node a, Int# #)` and the like, `I#` taken apart by hand, primops called directly) was
needed, or whether GHC does as well with ordinary code. No evidence had been collected
when it was written. This is the measurement.

Everything was rewritten to ordinary pairs and `Int` (strict where the value flows on), the
`casIntArray#` compare-and-swap stayed as the one small helper `Bytes.casUsed`, and the
`joinChunks` in Text.hs was rewritten with `Data.Primitive` instead of the raw primops. Then
the package's own benchmarks (`lib/unison-util-rope/benchmarks`, `stack bench --work-dir
.stack-work-bench unison-util-rope`, a work directory of its own so that enabling the
benchmarks does not unregister the optimized tree) were run on the commit before the
rewrite, in a worktree, and on the rewrite. Optimized build, same machine, one run each
with repeats of the rows that moved.

## The deque

All 72 deque rows within 3% of before, the `Data.Sequence` control rows moving by the same
amounts: lookup, take, drop, uncons and unsnoc at 10, 100, 10,000 and 1,000,000 elements
are 0.99 to 1.02×. GHC's constructed-product-result analysis unboxes these results on its
own; the hand-written unboxed tuples bought nothing. They are gone.

## The rope

Median 1.00× over the 72 rows that could be matched by name, with one real regression:
taking a text apart a character at a time, which goes through `chunkAt` (the lookup of the
chunk holding a character) for every character, was 1.05× at 1,000 characters and 1.07 to
1.08× at 100,000 and 1,000,000, in two runs each, while unconsing whole chunks was unchanged.
`chunkAt` and its helper `lookR` return a chunk and an offset from a local recursive loop
inside an `INLINEABLE` function, and the pair that GHC unboxes elsewhere was allocated here.
Those two functions keep the unboxed form, with a comment saying why; with them restored
the rows are back to 0.96 to 1.00×, and `index` and `drop` are 0.98 to 1.01× at every size
(a lone 1.08 on `drop` at 1,000 was noise: two further runs gave 0.99).

## Text and bytes

`joinChunks` with `Data.Primitive` and `casUsed`: the text append rows of the JIT suite and
the compare below say whether it cost anything.

## The JIT suite

Optimized build, `--jit on`, one run of `jit-benchmarks.md` against the run just before
the rewrite (the "one unit" column of [2026-10-19 C split](2026-10-19-c-split.md)). With
the JIT on most of these rows run the C helpers rather than the Haskell rope, so the
microbenchmarks above are the real test of the Haskell; this is the check that nothing the
interpreter still does moved.
