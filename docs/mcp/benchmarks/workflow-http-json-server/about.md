Tests whether the worker can pick libraries from Unison Share for a job it is only described (an HTTP service with JSON in and out) and use them well. No library is named in the prompt. The prompt fixes only the definition name `sumService`, so the judges can find it.

A good run: `share-project-search`, read the README of `@unison/routes`, `lib.install`, a `Route` handler (`noCapture POST (s "sum")`, `bodyUtf8`, `Decoder.run`, `ok.json`), a test through `harness` that opens no port. Traps: `@unison/httpserver` ranks first and is archived; the route names are not guessable; `decodeJson` raises, and the failure does NOT become a 400 (I checked: through `harness`, which runs `Route.run`, a bad body comes back as an exception, so the worker must catch it and answer with `badRequest.text` or `raiseBadRequest`; `workflows.md` had this wrong); installing `@unison/json` next to `routes` gives a second `Json` type, the nested copy is better; starting a server and hanging.

Judges: `outcome`, `library-choice` (GREAT routes plus json, PASS other sound combination, FAIL hand-built JSON or archived library), `behavior` (calls `sumService` through `harness`, in memory, no port; verified on the good run and on both bad ones), `docs-present`. The prompt does not ask for docs; the judge is there as in the other tasks.

Needs the network at the worker's run (search and install, 30 seconds for `routes`); no `setup.md`, the base codebase is the start. The judges work offline. Validated: `good.md` (routes 7.0.2, pinned), `bad-no-400` (behavior fails), `bad-handrolled` (routes for plumbing, hand-parsed body: library-choice fails, behavior fails). Not validated: no variant built on `@unison/httpserver` or on `@unison/http` directly (the PASS route); the library-choice judge's text for them is untested. No real worker has run this task, so I do not know how often it finds `harness` or the 400 trap. The `behavior` judge's fallback for a service that is not a `Route` computation is vague on purpose.
