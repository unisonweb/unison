Tests moving a real Share library to its latest release: `parseNats` uses `@unison/json` 1.2.1 (pinned in `setup.md`), and the prompt says "the latest release" with no number. The worker must find the newest release, `lib.install` it and `upgrade` the old folder to it, ending with exactly one json folder.
Decision on "latest": the prompt says latest, as a developer would. The judges don't hardcode a version: `outcome` calls the Share tool `share-project-info` for `@unison/json` and expects `unison_json_<latestRelease with underscores>` (1.4.2 today, 2026-10-30), so a newer release published later still judges correctly. The setup stays deterministic because the old version is pinned.
Needs the network at setup (about 20 s) and at the worker's run, and the judge's `outcome` needs the Share tool too. 1.2.1 to 1.4.2 upgrades cleanly (no temporary branch), so this is the easy upgrade; the hard one is `workflow-lib-upgrade-conflict`.
Good run: `list lib`, `lib.install @unison/json/releases/latest`, `upgrade unison_json_1_2_1 unison_json_1_4_2`, `test`. Traps: installing and stopping with two copies (`validation/bad-two-copies.md`), deleting the old folder by hand so `parseNats` points at an unnamed hash (`bad-deleted-old.md`), upgrading to an older release (`bad-not-latest.md`). All three show as FAIL on the `outcome` commands (checked by running them).
Judges: `outcome`, `behavior`, `no-collateral`. Topics: `ucm/libraries`, `ucm/upgrade`, `ucm/share`.
Risk: a future release of `@unison/json` could break `parseNats` (the upgrade would then not finish and the task becomes the conflict variant); `behavior` and `outcome` would still judge it correctly if the worker fixed it. I did not check what `lib.install ... releases/latest` does for a worker that doesn't pass a version, but `learn ucm/libraries` documents it.
