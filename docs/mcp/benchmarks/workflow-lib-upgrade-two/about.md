Tests `upgrade` with two libraries at once. The prompt is one sentence ("upgrade the dependencies `textkit` and `tally` to 2.0.0"); the judges state the behavior and test facts. `textkit` 2.0.0 changes `Label` (a second field); `tally` 2.0.0 is built on `textkit` 2.0.0 (each release carries its own copy of the `textkit` it was built with in its own `lib`, as real libraries do) and also changes `tick` to take an amount first. The project mixes them in `heading`, which gives the `Label` that `tally` returns to `textkit`'s `shout`.

What I verified with the real binary. The combined `upgrade textkit_1_0_0 textkit_2_0_0 tally_1_0_0 tally_2_0_0` leaves one file (`countThree`, `excite`, `heading`, `report` and their tests); only `countThree` needs a real change (`tick 1`), so one `load` and one `update` finish it. Upgrading one library at a time can NOT be made to fail outright: after `upgrade tally_1_0_0 tally_2_0_0` the file's `heading` has `textkit_1_0_0.shout` applied to `tally_2_0_0.title`'s `Label` (a different type), but the worker can fix that by hand with `textkit_2_0_0.shout` (both 2.0.0 releases are already in `lib`), and then `upgrade textkit_1_0_0 textkit_2_0_0` finishes by itself (`validation/bad-one-at-a-time.md`).
