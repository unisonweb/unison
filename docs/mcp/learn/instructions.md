This server runs Unison [transcripts](learn:ucm/transcript). These are Markdown documents with two kinds of fenced code blocks: `ucm` blocks give commands for [UCM](learn:ucm) (the Unison Codebase Manager), one per line, as in `> view foo`, and `unison` blocks give code to typecheck and expressions to evaluate. Anything you can do at the UCM command line you can do here. You get the transcript back with UCM's output after each command.

The Unison `learn` MCP tool explains all of this in whatever level of detail you want. Call it with a topic path, like `learn("ucm/merge")`, or with an empty path for an overview of all the topics. A topic gives a short summary and an index of its subtopics. Add `/detail` to the path for more, as in `ucm/merge/detail`. A link like [transcripts](learn:ucm/transcript) points to a topic: the text after `learn:` is the path to pass to `learn`. Look up topics as you need them, starting with [transcripts](learn:ucm/transcript) before your first call, and whenever something is unfamiliar.

The essentials:

- The four `transcript` tools differ only in which commands they allow within `ucm` blocks. Start with `transcript-read-only`; if a command isn't allowed, nothing runs and the reply names the tool you need. See [the tools](learn:ucm/transcript).
- A line like `> view foo` runs on the current project and branch, so you can start working at once: there's no need to look up the project first. Send several commands in one `ucm` block.
- Code in a `unison` block is only typechecked. It isn't saved or visible to subsequent blocks until you run [`update`](learn:ucm/update). Open and close `unison` blocks with four backticks (```` ```` unison ````), because documentation has three-backtick fences of its own, and those would end the block.
- **If the task needs something base doesn't have (JSON, a web server, dates, a file format), look for a published library on Unison Share and use it, instead of writing a parser or protocol yourself:** see [libraries from Share](learn:skills/library).
- **Before you write a function, look for one that already does it.** The base library has an answer to most common jobs (list and text processing, errors, randomness, mutable state, concurrency), and a hand-written version is longer and usually worse. Search with `find.all` and by type, and read the topic for your area (see [reuse](learn:skills/reuse)). If one of them does what you were asked for, even under another name, don't write it again: define the requested name as that function (`List.keepIf = List.filter`), with documentation and tests.
- **Read the topic for each area your task touches, before you write code:** [lists, maps and sets](learn:lang/collections), [text and parsing](learn:lang/text), [failure and missing values](learn:lang/errors), [new types and records](learn:lang/data), [abilities, handlers and higher-order functions](learn:lang/abilities), [mutable state and counters](learn:lang/mutable), [random numbers](learn:lang/random), [things at the same time](learn:lang/concurrency), [numbers](learn:lang/numbers) (use `Nat`, not `Int`, unless values can be negative), [layout](learn:lang/layout) when code doesn't parse, and [refactoring](learn:skills/refactor) when you change a definition that others use.
- **To change code that exists, change it and let UCM show you what that breaks:** send the new definition, `update`, then `test`. Don't read every dependent first, and don't retype definitions you aren't changing (see [update](learn:ucm/update)).
- **Read the topic for the UCM job before you do it:** [update](learn:ucm/update) (changing a definition others use), [merge](learn:ucm/merge) (bringing a branch in), [upgrade](learn:ucm/upgrade) (moving to a new version of a library, with `upgrade`, not by hand), [libraries](learn:ucm/libraries), [branches](learn:ucm/branches), [history and undo](learn:ucm/history), [rename and delete](learn:ucm/rename-and-delete), [find](learn:ucm/find). These commands do more than their names say, and doing them by hand loses things.
- **Document and test everything you add, even when the prompt says nothing about docs or tests** (unless it says not to): documentation for each new definition (see [documentation](learn:lang/documentation)) and tests that cover the edge cases and the failure cases, not only the example you were given (see [testing](learn:testing)). Write tests with `test.verify do` and `ensureEqual`, not `expect` or `expectU`, which don't exist. Run the tests.
- Work in the current project and don't create projects. Before you install a library, check that `list lib` doesn't already show it.
- Always give a command its arguments (`view foo`, never bare `view`), and don't write the output yourself.
- A command that fails stops the transcript, and a name that doesn't exist fails. To read a whole area in one call, `find-in Foo` lists everything under `Foo` with its tests, and `view 1-20` then shows those results with their documentation (see [find](learn:ucm/find)).
- For longer inputs, write the transcript to a temp file and pass `transcript-file`, so if there are errors you can fix one spot and easily run it again.
- In a `ucm` block, `help <command>` shows a command's usage. `help` with no arguments prints help for every command (over a thousand lines, so you get a file path back to grep). Mark a block ```` ``` ucm :error ```` if you expect it to fail.
